# Crash Fix: macOS HIToolbox Dispatch Queue Assertion Failure

**Date:** 2026-01-22  
**Issue:** EXC_BREAKPOINT (SIGTRAP) - `_dispatch_assert_queue_fail` in HIToolbox  
**Platform:** macOS 15.6.1 (affects all macOS versions)

## Problem Summary

The application was crashing with a dispatch queue assertion failure when the automation worker thread (QThread) tried to initialize pynput's `KeyboardController` or `MouseController` for the first time.

### Crash Stack Trace
```

```

## Root Cause

On macOS, the `pynput` library's `KeyboardController` and `MouseController` internally access macOS **HIServices APIs** (specifically `TSMGetInputSourceProperty`) during initialization to detect the keyboard layout and input sources.

These HIServices APIs **must run on the main thread**. macOS enforces this requirement using Grand Central Dispatch (GCD) queue assertions. When these APIs are called from a background thread, the system triggers a `dispatch_assert_queue_fail` crash with signal SIGTRAP.

The issue occurred because:
1. The pynput controllers were lazily initialized (created on first use)
2. First use happened in the worker thread (QThread) when `click_point()` or `paste_text()` was called
3. Controller initialization tried to access HIServices APIs from the worker thread
4. macOS detected the violation and crashed the application

## Solution

Pre-initialize the pynput controllers on the main thread during application startup, before any worker threads are created.

### Changes Made

#### 1. `app/core/os_adapter/input_inject.py`

Added a new function to initialize the controllers on the main thread:

```python
def init_input_controllers() -> None:
    """Initialize pynput input controllers on the main thread.
    
    MUST be called from the main thread before any worker thread uses input injection.
    On macOS, pynput's controllers access HIServices APIs during initialization,
    which must run on the main thread to avoid dispatch_assert_queue crashes.
    
    Typically called during application startup.
    """
    import sys
    try:
        print(f"[INIT] Initializing input controllers on main thread...", file=sys.stderr)
        # Force initialization of both controllers on main thread
        _ = _get_mouse()
        _ = _get_keyboard()
        print(f"[INIT] Input controllers initialized successfully", file=sys.stderr)
    except Exception as e:
        print(f"[INIT] Warning: Failed to initialize input controllers: {e}", file=sys.stderr)
        import traceback
        traceback.print_exc()
```

#### 2. `app/main.py`

Called the initialization function after QApplication creation but before showing the main window:

```python
# Initialize clipboard helper on main thread (required for worker thread clipboard access)
from app.core.os_adapter.input_inject import init_clipboard_helper, init_input_controllers
init_clipboard_helper()

# Initialize pynput controllers on main thread (macOS requires this to avoid crashes)
# pynput accesses HIServices APIs during controller initialization which must run on main thread
init_input_controllers()
```

## Why This Works

By initializing the controllers on the main thread:
1. All HIServices API calls happen on the main thread during startup
2. The controllers are created and cached in the global variables `_mouse` and `_keyboard`
3. When the worker thread later calls `_get_mouse()` or `_get_keyboard()`, it gets the pre-existing controllers without triggering initialization
4. No HIServices APIs are called from worker threads, avoiding the dispatch queue assertion

## Additional Notes

- This fix applies the same pattern already used for the clipboard helper (`init_clipboard_helper()`)
- The fix is macOS-specific but doesn't harm other platforms (Windows/Linux will simply initialize the controllers on the main thread as well)
- This is a common pattern when working with native APIs that have thread affinity requirements
- Similar issues can occur with other macOS frameworks (CoreGraphics, CoreFoundation, etc.)
